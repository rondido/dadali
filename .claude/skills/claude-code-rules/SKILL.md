# Claude Code 룰 관리 가이드

룰을 추가하거나 관리할 때 다음 지침을 따릅니다.

## 룰이란

룰은 `.claude/rules/` 디렉토리에 저장하는 **주제별 마크다운 지침 파일**입니다. CLAUDE.md를 모듈화한 것으로, 파일 패턴에 따라 조건부 로딩이 가능합니다.

### 룰 vs CLAUDE.md vs 스킬

| | 룰 | CLAUDE.md | 스킬 |
|---|---|---|---|
| 저장 위치 | `.claude/rules/*.md` | `CLAUDE.md` | `.claude/skills/` |
| 로딩 | 조건부 (path 기반) 또는 무조건 | 항상 전체 로딩 | 온디맨드 |
| 용도 | 주제별 지침 모듈화 | 프로젝트 전체 지침 | 호출형 워크플로우 |
| 컨텍스트 비용 | path 매칭 시에만 소비 | 항상 소비 | 트리거 시에만 |

**사용 기준:**
- **CLAUDE.md**: 모든 상황에 적용되는 프로젝트 전체 지침 (200줄 이하 유지)
- **룰**: 특정 파일/주제에만 적용되는 지침, CLAUDE.md가 커질 때 분리
- **스킬**: 반복적인 워크플로우, 호출형 작업

## 룰 위치

| 위치 | 경로 | 적용 범위 | 우선순위 |
|------|------|----------|----------|
| 전역 (개인) | `~/.claude/rules/` | 모든 프로젝트에 자동 적용 | 낮음 |
| 프로젝트 | `.claude/rules/` | 해당 프로젝트만 | 높음 (나중에 로딩되어 우선) |

하위 디렉토리의 `.md` 파일도 재귀적으로 탐색됩니다.

## 룰 파일 형식

### 무조건 로딩 (frontmatter 없음)

```markdown
# 코드 스타일 규칙

- 2칸 들여쓰기 사용
- 줄 길이 100자 이하
```

세션 시작 시 항상 로딩됩니다.

### 조건부 로딩 (paths 지정)

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/handlers/**/*.ts"
---

# API 개발 규칙

- 모든 엔드포인트에 입력 검증 포함
- 표준 에러 응답 형식 사용
```

매칭 파일을 읽을 때만 로딩됩니다.

### paths 글로브 패턴

| 패턴 | 매칭 대상 |
|------|----------|
| `**/*.ts` | 모든 하위 디렉토리의 .ts 파일 |
| `src/**/*` | src/ 아래 모든 파일 |
| `*.md` | 루트의 .md 파일만 |
| `src/**/*.{ts,tsx}` | .ts와 .tsx 모두 매칭 |

**주의:** YAML에서 `*`이나 `{`로 시작하는 패턴은 반드시 따옴표로 감싸야 합니다.

```yaml
# 올바른 예
paths:
  - "**/*.ts"
  - "src/**/*.{ts,tsx}"

# 잘못된 예 (YAML 파싱 오류)
paths:
  - **/*.ts
```

## 로딩 동작

### 로딩 순서

1. `~/.claude/rules/`의 무조건 룰
2. `.claude/rules/`의 무조건 룰
3. CLAUDE.md 파일들
4. (파일 읽기 시) 매칭되는 path 기반 룰

나중에 로딩되는 지침이 더 높은 우선순위를 가집니다.

### 알려진 제한사항

- **Write 도구 비대칭**: path 기반 룰은 `Write`로 새 파일 생성 시에는 로딩되지 않음. `Read`/`Edit` 시에만 트리거됨.
- **서브에이전트 전파 없음**: 전역 룰은 서브에이전트에 자동 전파되지 않음.

## 룰 작성 원칙

### 1. 파일당 하나의 주제

```
.claude/rules/
├── code-style.md      # 코드 스타일만
├── testing.md         # 테스트만
├── security.md        # 보안만
└── frontend/
    ├── react.md       # React만
    └── styling.md     # 스타일링만
```

### 2. 200줄 이하로 유지

개별 룰 파일은 200줄을 넘지 않도록 합니다. 길어지면 하위 주제로 분리합니다.

### 3. 구체적이고 검증 가능하게

```markdown
# 좋은 예
- 모든 API 엔드포인트는 zod 스키마로 입력을 검증합니다
- React 컴포넌트 파일은 PascalCase로 명명합니다

# 나쁜 예
- 입력을 적절히 검증합니다
- 컴포넌트를 잘 정리합니다
```

### 4. 마크다운 헤더로 구조화

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 개발 규칙

## 입력 검증
- zod 스키마 사용
- 처리 전에 검증

## 에러 처리
- 표준 에러 형식 반환
- 컨텍스트와 함께 로깅

## 문서화
- JSDoc 주석 포함
```

### 5. 충돌 방지

여러 룰 파일이 같은 주제를 다루지 않도록 합니다. 관련 룰 파일 간 모순이 없는지 확인합니다.

## 룰 추가 워크플로우

### 새 룰 추가 시

1. 주제 결정 및 적용 범위 파악
2. path 기반 조건부 로딩이 필요한지 판단
3. 룰 파일 작성 (200줄 이하)
4. 기존 룰과 충돌 여부 확인

### 룰 수정 시

1. 기존 룰 내용 확인
2. 변경 사항 반영
3. paths frontmatter가 유효한지 확인

### 룰 삭제 시

1. 룰 파일 삭제
2. 다른 룰이나 CLAUDE.md에서 참조하는 곳이 있으면 함께 정리

## CLAUDE.md에서 룰로 분리

CLAUDE.md가 200줄을 넘거나 주제가 5개 이상이면 룰로 분리를 고려합니다:

1. CLAUDE.md에서 주제별로 내용 그룹화
2. 각 그룹을 `.claude/rules/주제.md`로 추출
3. path 기반 스코핑이 가능한 것은 `paths` 추가
4. CLAUDE.md에는 프로젝트 개요, 빌드 명령 등 핵심만 남김

## 디렉토리 구성 패턴

### 소규모 프로젝트

```
.claude/rules/
├── code-style.md
└── testing.md
```

### 대규모 프로젝트

```
.claude/rules/
├── universal/           # paths 없음 (항상 로딩)
│   ├── code-style.md
│   └── security.md
├── frontend/            # paths: "src/components/**"
│   ├── react.md
│   └── styling.md
└── backend/             # paths: "src/api/**"
    ├── api-design.md
    └── database.md
```

## 이 프로젝트에서의 룰 관리

이 프로젝트는 전역 룰을 Git으로 관리합니다:

1. `rules/` 디렉토리에 `.md` 파일 추가 (하위 디렉토리 가능)
2. `yarn sync` 실행하여 `~/.claude/rules/`에 동기화
3. `yarn status`로 차이 확인
