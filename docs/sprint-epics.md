# 다달이 MVP 에픽·태스크 정리

> 출처: 「다달이 서비스 기획서」. 괄호 안 F·P 번호는 기획서의 기능 ID와 화면 ID다.
> Next.js·Drizzle·Supabase 폴더, API 확인 스크립트(`npm run explore`), 테스트 환경은 이미 세팅되어 있다.

## E1. 기반 세팅과 인프라
- [ ] FullCalendar 패키지 5개 제거 (아직 `package.json`에 남아 있음)
- [ ] Supabase 프로젝트 연결, 환경변수와 GitHub Secrets 정리 (서비스 키, 공공데이터 인증키)
- [ ] Vercel 배포 파이프라인 연결
- [ ] 공통 레이아웃: 헤더, 하단 고지("정부 공식 서비스 아님", "정확한 자격·일정은 공식 사이트 공고를 따름")
- [ ] 디자인 토큰: 분야 4색(cat-1~4), 마감 임박 빨간색, 명도 대비 4.5:1, 터치 영역 44px
- [ ] 도메인(dadali.kr / .com)과 KIPRIS 상표 확인 *(업무)*

## E2. 데이터 모델과 DB
- [ ] Drizzle 스키마 작성: Notice, Site, Event, RegionAgency, Category, SyncLog, Dictionary, UnknownTerm
- [ ] Notice 검색용 필드: `summary_text`, `topics`, `search_vector`(tsvector 자동 생성)
- [ ] 공통 필터 필드: `age_groups`, `region_codes`, `industries`, 예약 필드 `sigungu_code`
- [ ] 확장 기능 활성화: pg_trgm, 전문 검색 인덱스
- [ ] RLS 설정: anon은 읽기만, 쓰기는 서비스 키만
- [ ] URL 도메인 검증 규칙 (go.kr·or.kr과 예외 목록만 허용)
- [ ] 시드 데이터: Category 4개, Site 10곳(접속·도메인 재확인 포함), Event E01~E10

## E3. 공고 수집 파이프라인
- [ ] 두 API(K-Startup, 행안부 혜택)의 실제 응답 확인: 상시 공고 비율, 지원 내용 요약 필드가 있는지
- [ ] K-Startup 수집기: 받은 뒤 지역으로 다시 거르기
- [ ] 행안부 공공서비스(혜택) 수집기
- [ ] 변환 규칙
  - 날짜: 날짜 없음, "상시", "예산 소진 시"는 `is_always`로 처리. 해석에 실패하면 `parse_status=check`
  - 신청대상 → 나이대, 지역명 → 시·도 코드, 업종 문구 → 업종 묶음
  - 지원 내용 → 300자 요약 + `topics`
- [ ] upsert 규칙: `source + source_id` 기준, `is_locked`인 공고는 건너뜀, 원본 응답(`raw_payload`) 보관
- [ ] 소스 간 중복 제거 (공고명·주관기관·마감일이 같으면 하나만, 상세 URL 있는 쪽 우선)
- [ ] 소스별로 따로 실행해 하나가 실패해도 나머지 반영, SyncLog 기록, 실패하면 운영자에게 메일
- [ ] GitHub Actions 스케줄 (새벽 5시, 1~3월에는 하루 2회)
- [ ] 수집이 끝나면 ISR 재생성 호출

## E4. 자유 입력 해석 엔진 (F02, F07)
- [ ] 법정동코드 파일로 지역 사전 생성 (시·군·구, 읍·면·동 → 시·도 코드 앞 2자리, 별칭 포함)
- [ ] 표준산업분류와 동의어로 하는 일 사전 생성 (업종 묶음 6개)
- [ ] 관심 주제 사전 (9개 주제)과 나이대 규칙 (숫자·단어 → youth / middle / senior)
- [ ] 문장 정리: 조사와 띄어쓰기 처리
- [ ] 해석 Route Handler: 문장 → 조건 값, Zod로 결과 검증
- [ ] 애매한 지명은 선택지로 묻기 ("광주"), 오타는 pg_trgm으로 비슷한 단어 제안
- [ ] 남은 단어 검색 (공고명·요약 대상 전문 검색)
- [ ] 필터 규칙: 조건 사이는 AND, 관심 주제끼리는 OR, 빈 값은 전체 대상으로 통과
- [ ] 입력 문장을 로그·DB에 남기지 않는지 확인
- [ ] 해석 엔진 단위 테스트 (시나리오 문장 세트)

## E5. 첫 화면과 검색 결과 (P01, P02 / F01, F03, F04, F11)
- [ ] 첫 화면: 큰 입력창, 예시 문장 버튼 4개, "저장하지 않아요" 고지
- [ ] 입력 전 화면: 진행 중 N건, 이번 주 마감 N건, 이번 주 마감 카드 3개, "전체 지원사업 보기"
- [ ] "이렇게 이해했어요" 해석 칩: 종류 라벨, 진한 칩과 테두리 칩 구분, ×를 누르면 바로 다시 걸러짐
- [ ] "+ 조건 추가" (지역·나이대 등 직접 고르기)
- [ ] 못 알아들은 말 안내, 결과 0건이면 뺄 만한 칩 제안
- [ ] 결과 제목 "조건에 맞을 수 있는 지원사업 N건"

## E6. 상태 보드 (P03 / F05, F06, F09)
- [ ] 상태 판정 로직 (진행 예정, 진행 중, 상시)과 열별 정렬, 마감 공고 제외
- [ ] 카드: 분야 태그, 상태 배지, D-day(7일 이내 빨강, 당일 "오늘 마감"), 진행 막대, 왜 걸렸는지 태그
- [ ] 보드 위 요약 ("이번 주 마감 N건 · 7일 안에 시작 N건")
- [ ] 열별 더보기 (상위 N건 + "N건 더보기"), 열 제목에 건수
- [ ] 상시 공고가 너무 많으면 별도 탭으로 분리 (E3의 API 확인 결과로 결정)
- [ ] 조건 저장: URL 쿼리(`region/age/biz/topic`)와 localStorage, 재방문하면 바로 보드
- [ ] 전체 보드: 저장된 칩, "조건 바꾸기", 우리 지역 지원기관 카드
- [ ] 끌기 손잡이를 두지 않고 "칸반"이라는 말을 쓰지 않음

## E7. 공고 상세와 기간 달력 (P04 / F08, F10, F12)
- [ ] 상세 헤더: 분야·상태, 공고명·기관, 큰 D-day, "15일 중 4일째"
- [ ] 기간 달력 직접 구현 (date-fns): 막대, 지난 기간과 남은 기간 진하기, 오늘 테두리, 시작·마감일 원
- [ ] 여러 달 처리: 두 달은 나란히(모바일은 위아래), 세 달 이상은 "… N주 …"로 접기
- [ ] 대상 태그, 출처, 최종 갱신 시각(SyncLog), "세부 자격은 원문 확인" 안내
- [ ] 원문 공고 보기: 새 탭으로 열고, URL이 없거나 깨졌으면 소스 사이트 메인으로 보냄
- [ ] 링크 클릭 수 익명 집계

## E8. 사이트 소개와 지역 기관 (P05 / F13, P2)
- [ ] 17개 시·도별 지원기관 1~3곳 조사 후 RegionAgency 입력 *(조사 업무)*
- [ ] 사이트 소개 페이지: 분류 탭 + 공식 사이트 카드 10곳, 운영기관 표시 (sbiz24.kr은 공식 여부 표기)

## E9. 모바일, 접근성, 운영, 출시
- [ ] 모바일 대응 (P06): 상태 탭(기본은 진행 중), 한 열 레이아웃
- [ ] 접근성: 키보드로 칩 빼기와 카드 열기, × 버튼 읽기 라벨 ("서울 조건 빼기")
- [ ] 못 알아들은 단어 집계 (F14, P2): 숫자·2글자 이하·사람 이름처럼 보이는 단어 제외
- [ ] 지표 수집: 해석 성공률, 칩 제거율, 결과 0건 비율, 이동 클릭률. 목표 수치는 따로 확정
- [ ] 운영용 Supabase 저장 SQL: 확인 필요 공고, 숨김 처리, `verified_at`이 180일 지난 항목 경고
- [ ] 월 1회 링크 점검 스크립트 (`link_status`)
- [ ] E2E 테스트 (대표 시나리오 3개), SEO 메타("다달이 - 내게 맞는 정부지원사업")
- [ ] 연중 시기 E01~E10을 당해 공고로 검증 *(업무)*

## 스프린트 순서 제안

1. **S1: E1, E2, E3 앞부분.** API 응답을 먼저 봐야 상시 탭 분리 여부와 `summary_text` 출처가 정해지고, 이 결정이 E3·E6에 영향을 준다.
2. **S2: E3 마무리, E4.** 실제 데이터와 해석 엔진을 갖춘다.
3. **S3: E5, E6.** 핵심 화면인 첫 화면, 검색 결과, 보드.
4. **S4: E7, E8, E9.** 상세 화면을 붙이고 다듬어 출시한다.
